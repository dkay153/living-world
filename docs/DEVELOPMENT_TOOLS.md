# Development tools and continuation

Studio Stop cancels the active run and pauses development scheduling. It retains an explicit suspended-run ID, independently of the newest question. Ask remains available only for an already activated, connected and verified developer with a suspended run; it does not enable background development. Questions receive the suspended objective/public update and bounded retained edit data when available. Resume (or an Agent-mode message while paused) uses that task ID, restores the saved execution setting and starts a fresh plan/review with retained source as untrusted data. Public Q&A since Stop is supplied as context. Old checks, leases and release claims confer no authority. This is continuation of work, not resuming an interrupted instruction or replaying a paid turn.

The host supplies `.scratch/developer-tool.cjs` during planning and implementation. Write a request JSON in scratch and run `node .scratch/developer-tool.cjs @.scratch/request.json` using the permitted command shell. Read its returned source hash, actual exit/timeout/output and artifact paths. These are development receipts, never independent release approval.

Supported requests:

- `{"action":"prepare"}` verifies the installed locked Node/npm/Next/Playwright/Chromium environment and production build.
- `{"action":"test","tests":["tests/game.test.js"]}` runs top-level tests inside the isolated worker.
- `{"action":"contracts"}` validates contracts; `{"action":"build"}` builds production UI.
- `{"action":"packages","add":["pngjs@7.0.0"]}` installs exact registry development tools in a separate profile. Use `remove:["pngjs"]` to remove obsolete extras, including their transitive modules. Lifecycle scripts are disabled. The provisioning container has registry network access and no candidate source/account/history mounts. Candidate execution remains offline and unprivileged. Profile volumes are removed when the model turn ends.
- `{"action":"command","argv":["node","scripts/my-check.js"],"artifacts":[".scratch/capture.png"]}` runs node/npm/sh arguments in a disposable writable copy. Up to three validated scratch PNGs return to the original candidate for view_image. No command is executed on the owner host. Edits in this disposable worker are not automatically written back or published.

Requests run serially, with up to sixteen extra tools and eight package changes per package request. Commands have bounded output, execution time and resource use. Owner Stop and saved run/time/account controls remain authoritative; there is no arbitrary cumulative twelve-request phase cutoff. Failed checks remain failures. A missing package must be provisioned or a specific unsupported capability explained; it is not evidence of passing validation.

Production dependency manifests/images use the separately verified `dependencies` path described below. OS/admin installation and independent kernel/account authority remain separate capabilities. Never silently use a development profile as a production image.

Next generates next-env.d.ts for both dev and build. Capture canonicalizes only the exact known generated template to production references; arbitrary extra declarations stay visible to integrity checks. Tailwind scans only app/components, and Next 16.4 uses its native .next/dev output separation; Tailwind source registration excludes unrelated candidate trees. The optional CLI debug prompt encoder is no longer a prerequisite: local PNG checksum/format/pixel/decompression checks validate host-produced images without a CLI session or model call.

Request JSON is bounded to 8 KiB. Use small inline planning probes; approved source scripts can hold larger diagnostics during implementation. The supplied transport anchors paths to its own workspace and combines stderr with stdout only for offline commands, so a shell starting elsewhere or a failed check does not silently lose its diagnostics. These are development-tool constraints, not evidence that an unexecuted check passed.


## Full development runtime (17 October)

The project skill `.agents/skills/game-development/SKILL.md` explains browser journeys, tool installation and environment recovery. `scripts/play-game.js` provides an extensible starting point: invoke it through the contained command tool with a JSON journey, select `/` or `/legacy/`, desktop/mobile dimensions, keyboard/click/assertion/reload steps and a scratch PNG. It starts a disposable private micro world and Chromium, returns visible text and browser diagnostics, then tears down its server/database. Export the PNG through `artifacts` and inspect it. Richer Playwright programs can live under scripts/ or tests/ and run with the same tools; the helper's action vocabulary does not restrict those programs. Discovery of installed skills is not proof every desktop plugin is connected to the project account. Missing external services/access must be reported precisely, never silently claimed.

The account worker uses the installed Codex App Server harness. Native tools, public item events, skills discovery and turn interruption belong to Codex. Terminal native conversations may be forked into a fresh sandbox for continuation. An uncertain native turn is never replayed. Planning, implementation acceptance, isolation, owner settings and independent release checks remain separate host responsibilities. Project skills in `.agents/skills` are captured, editable and discoverable; they cannot grant host permissions.

For production packages, request `{"action":"dependencies","add":["pngjs@7.0.0"],"remove":[]}` during implementation. This generates candidate package/lock data in a separate registry container with scripts disabled. Only dependency declarations may change in package.json. Changed versions must be exact, and the npm v3 lock must bind registry tarballs with SHA-512 integrity (bundled entries inherit a verified parent). No git/file/URL packages, candidate Dockerfile, npm hooks or arbitrary host installation. Development-only extras still use `packages` and are removed at phase end.

Build/test/command checks use the candidate production dependency image automatically. Independent staging builds the exact same immutable image and tests the complete source and browser/history journey. Trusted controller/observer dependencies remain on their original immutable tree; new packages are only game/test/build or confined operator inputs. A release pairs exact source, build and image. Deployment failure retains the prior runtime. Fault rollback boots its predecessor image with the latest acknowledged checkpoint, never an older player backup. Images required by current/previous artifacts are retained.

For host recovery request `{"action":"host","service":"docker","operation":"inspect"}` or `repair`; service `realm` is also supported. These invoke fixed host capabilities, with readiness verification, durable audit and backoff. They cannot pass shell commands, executable paths or arbitrary downloads. The desktop launcher supervises only its own owner/renderer children and restarts crashes with backoff; closing the launcher stops them deliberately. Host administrator access, credentials, owner settings and the independent kernel are not self-granted.

Unsuccessful release checks and failed/interrupted work can trigger a new autonomous diagnosis with retained evidence/source, a fresh plan, explicit seed acceptance and every release gate. It checks saved activation, current selectable model, provider allowance and isolation again. Backoff is five minutes, extending to six hours after two repeated repairs. Owner Stop and question-only runs never auto-restart. Account authentication/allowance/model blockers wait for legitimate recovery rather than inference retries. Old failure records stay in memory.


Recovery conflicts now produce `mode: manual_rebase` in the recovery record with no prior files imported. The implementation can reconstruct an ordinary allowed fix from bounded retained text against current source, discard obsolete/protected old edits, and explicitly accept recovery before independent checks. Prior artifacts remain available for audit. Idle host maintenance reaps abandoned tool/stage containers by their exact read-only mount roots; it never removes canonical-world mounts, operator worlds, active jobs or source operations. Cleanup is serialized with scheduling and shutdown.
