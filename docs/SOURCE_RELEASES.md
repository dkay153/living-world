# Contained game-source releases

**16 October 2026:** Docker Desktop 4.95.0 and WSL 2.7.13 passed the real Linux-container deployment, acknowledged-progress, container-fault, rollback, host-restart and teardown drill. The pinned runtime uses Node 22.23.3. Enrollment applies only to the isolated local preview; authenticated world cutover and current running status are reported by the owner service. Model/budget settings and the saved account execution pause are preserved. Evidence is retained in `outputs/source-lane-verification/real-acceptance.json`.

## What this lane does

The developer can now submit an exact game-source artifact to a separate contained runtime, run a UI build, candidate tests and protected browser/saved-world journeys, then deploy that artifact and recover previous source without restoring an old player save. The existing paid account controls remain separate and unchanged. World Intelligence inference is still disabled.

The host source broker, owner APIs, credentials, model/budget records, runtime tools, dependency lock and release policy are outside candidate promotion authority. Ordinary game logic, combat, world, compatible persistence code, presentation and new game modules can use the lane. This does not let a candidate replace its validator or deploy changes to the owner/account control plane. Godot export and schema-changing releases remain outside this implementation.

## Trust and execution boundaries

- `server/release-artifacts.js` seals bounded, symlink-free source. Checksums cover the final candidate rather than the pre-edit baseline. Protected files are compared again after capture, independently of the candidate's change list. Tests/builds cannot silently alter the source that is later executed.
- `runtime/Dockerfile` is built only from a minimized trusted context: the existing package files and `runtime/`. It installs the locked dependencies and Chromium. No candidate Dockerfile, installation hook, owner database or account directory becomes an image input. Deployment uses a content-addressed image ID, never a mutable tag, and verifies tooling/dependency labels.
- Each container has no external network, no published port, no Docker socket, a read-only root, read-only source/seed mounts, private work filesystems, a process limit, and CPU/memory bounds. The game cannot write the host's canonical save. Docker's default capabilities are dropped; only UID/GID switching and ownership setup remain with the protected controller. Candidate execution runs as UID 10001; observation runs as UID 10002. The protected controller stays separate and never imports candidate JavaScript.
- Every launch runs filesystem/UID canaries and an external-network denial check before candidate execution. Chromium uses its sandbox with the versioned Playwright seccomp profile. A failed canary, missing kernel capability or browser failure blocks the lane; there is no host execution fallback.
- The protected controller runs fixed build/test commands, freezes a fresh source/output copy, and then starts the game under a fixed owner-free Realm entry. Check failures retain at most 6,000 characters of JSON-escaped diagnostic data; that text is never interpreted as protocol or release authority. Staging records success only after its container teardown is confirmed. New gameplay intents are data passed to the candidate game engine; they cannot request broker operations.
- Candidate tests are an additional check, not the protected verdict. The separate observer exercises Mara's quest, guard/retreat, malformed movement, reconnect, an existing active encounter and a completed veteran, plus actual React/canvas desktop and mobile captures. Legacy item sources remain unknown. This initial compatibility suite is intentionally narrow; it does not prove artistic improvement or permit every possible game redesign.

The seccomp profile derives from the Playwright v1.64.0 [official profile](https://github.com/microsoft/playwright/blob/v1.64.0/utils/docker/seccomp_profile.json), with an explicit `chroot` syscall allowance for Chromium's inner user namespace. No outer `SYS_CHROOT` or `SYS_ADMIN` capability is granted. A real probe verifies that outer chroot remains denied while Chromium sandbox startup succeeds. Runtime flags follow [Docker's run reference](https://docs.docker.com/reference/cli/docker/container/run/) and [Playwright's Docker guidance](https://playwright.dev/docs/docker).

Contained UI builds use webpack because Turbopack cannot resolve dependencies linked outside the sealed workspace. Tests run against the standard basin; only the independent browser journey uses the micro fixture. The controller clears inherited supplementary groups and freezes file ownership before copying output. Debian packages use the signed 15 October snapshot with signature/date/expiry checks enabled; dependency/tool updates require rebuilding and re-verifying the runtime.

## History and rollback

The host owns `DATA_DIR/source-lane/history/world.sqlite`. A running Realm gets a private copy, not writable access to that file. Before the gateway forwards an authoritative WebSocket reply, the controller exports a consistent SQLite checkpoint. The host verifies integrity, real canonical tables, unchanged schema, retained events/discoveries/knowledge, item origins and consumption, traveler continuity and completed progress. It flushes the new checkpoint file and atomically replaces the canonical copy before forwarding the reply. Stale runtimes cannot commit or acknowledge updates.

The gateway runs on a separate loopback origin, normally port 3200. It forwards only bounded game HTTP and WebSocket operations over the container's private stdio protocol. It never forwards an owner cookie, bearer header, arbitrary destination or owner API request. Existing guest identity cookies can carry into the game gateway, preserving the corresponding traveler. Owner UI remains on the original service origin.

Deployment holds new game traffic, saves the final old-runtime checkpoint, creates a consistent pre-deployment backup, and persists deployment intent. A new container starts against a copy of that checkpoint. Startup must retain existing player/battle state, preserve history and schema, reproduce the staged build hash, and pass readiness. Only then does the durable active pointer change and the gateway resume. A failed candidate leaves the previous runtime available. A runtime/history fault after publication starts previous source against the latest acknowledged checkpoint, not the older backup. With no previous revision, one guarded restart of the current verified source is attempted. Failed recovery leaves traffic held and history retained.

The ledger records pending deployment/rollback. Restart resolves that durable source pointer against the acknowledged world; an interrupted rollback chooses the previous source. The old mixed owner/world database is backed up and retained at initial cutover. The owning server stops accepting legacy game writes before canonical rows are copied, and persists that delegation so restart cannot create two writable worlds. Owner settings and secrets stay in the original control service and are not imported into the contained Realm. Canonical aggregate observations from the protected world feed subsequent independent task selection.

Schema-version and unversioned schema changes are rejected. Safely deploying a breaking schema change needs a separately verified forward/backward compatibility mechanism; restoring an old backup and discarding newly acknowledged progress is not an acceptable substitute. Full-checkpoint copying is a seed-scale implementation with a 48 MiB runtime export ceiling; public-scale incremental checkpoints, disk-loss durability and external service supervision remain further work. File flush plus atomic rename protects ordinary process interruption; it is not a claim of zero data loss after arbitrary host disk/power failure.

## Enrollment and operation

On a host with Docker running Linux containers, use the trusted checkout and the project's Node 22 runtime:

```powershell
# Select the same owner service data directory; never substitute its model settings.
$env:DATA_DIR = 'C:\path\to\the\owner-service\data'
node scripts/source-runtime.js build
```

The command builds and verifies the pinned runtime image, then runs a complete acceptance drill against synthetic data and an isolated temporary game port. It must stage a baseline and changed artifact, publish it, acknowledge a discovery only after the host checkpoint, kill the actual published container, recover automatically to previous source, restart the host lane and retain the discovery. Only a passing real drill writes enrollment into the selected owner service's source-lane configuration. A failed build/drill leaves live source authority unenrolled. It does not sign in, choose a model, change budgets or activate paid developer execution.

This machine's build used the `living-world-tools` Docker-container builder (`$env:BUILDX_BUILDER = 'living-world-tools'`). `node scripts/source-runtime.js verify` reuses the already-built local image only after its immutable ID, tooling and dependency labels match; it still repeats the complete real acceptance drill. Neither command enrolls from an old receipt. Receipt writing occurs after teardown completes. Initial tool-image setup has a separate 30-minute build timeout; owner account run limits are unchanged.

In the authenticated owner UI, open **Operations → Game releases**. Check the runtime, then choose **Verify protected runtime** when no game source is installed. This repeats protected baseline staging before quiescing/importing the owner's world. Cutover may take several minutes. Once running, the original world entry redirects to the contained game. **Restore previous game** uses the latest acknowledged checkpoint. These operations use the existing owner authentication, same-origin and CSRF checks.

The host preparation deadline allows five minutes for stage mode: its existing two-minute build and two-minute test deadlines run in sequence, followed by source freezing, copying and service health. Serve mode retains its three-minute preparation deadline. Individual check deadlines, CPU/memory/mount isolation, exact-artifact validation and account/model limits are unchanged. The host does not retry inference or relax a failed check. A deterministic delayed-ready regression verifies both completion after the old deadline and rejection at the new bounded deadline.

Future owner-enabled development uses the active released source as its baseline. Passing broader game candidates go through contained staging and automatic source deployment under the enrolled policy. Art-only work retains the existing visual-data lane. Paused account execution and the failure circuit are preserved; installing/enrolling a runtime does not secretly wake a model attempt.

The gateway also keeps validated art-data publication connected after cutover. A source release initially uses its exact staged art; a later host-validated visual revision can override that data without copying the owner database into the game. A source candidate is rejected if the visual baseline changed during its staging, and subsequent developer copies start from the art actually visible in the protected game.

The owner service relays only a typed pause flag for deterministic maintenance into a controller-owned read-only game control file; no model, budget or credential settings cross that boundary. Disaster recovery must preserve the source-lane ledger, artifacts and canonical history as well as the original control database. The original owner database backup alone is not a complete backup of a delegated game.

The legacy memory worker stops when the ownership flag is set; it cannot continue maintaining a second writable world. Shutdown aborts and awaits tracked release operations, keeps traffic held, confirms container removal with bounded polling, and then cleans up its own CLI client. Delayed CLI exit or asynchronous Docker removal is not treated as proof that a container stopped; daemon unavailability still blocks confirmation.

## Verification and current limitations

Evidence lives in `outputs/source-lane-verification/`: trusted suite output, release/gateway/drill tests, contract output, runtime availability, owner UI screenshot and browser result. Host tests cover source tampering, control-plane changes, links, failed startup, mismatched/stale evidence, schema refusal, historical rewrites, owner-data exclusion, unchanged model/budget fixtures, post-publication progress, rollback, stale workers and interrupted rollback/restart. The gateway test checks persistence-before-acknowledgment and credential isolation. The actual owner controls were rendered and visually inspected with a fresh disposable database.

The 16 October trusted suite passed 96/96 tests. The UI build, TypeScript and contracts passed; 24 focused lifecycle/history/worker/UI-entry regressions also passed. The real contained staging suite runs under Node 22.23.3, and the separate observer passed quest, guard/retreat, reconnect, malformed input, saved-encounter, veteran, desktop/mobile and accessibility checks. The real drill published source, acknowledged a discovery after its host checkpoint, killed the published container, rolled back, restarted and retained that discovery. Teardown was confirmed before the final acceptance receipt was written.

The isolated local preview is enrolled and cut over to port 3200; its owner service remains on port 3100. Post-cutover verification preserved both existing travelers and every recorded gameplay/history row. Exact developer/model/time/budget/autonomy setting hashes remain unchanged, the three earlier account attempts remain three, and no inference was activated. The missing API-budget record remains missing. Saved account execution and its failure circuit remain paused; successful release-path verification is not a successful autonomous model improvement.

No saved candidate code or tests ran outside containment. Trusted host/control verification used Node 24; authoritative game execution and candidate checks use the pinned Node 22 image. Production players were not moved. This is still a local, seed-scale release lane: schema-breaking changes, host/account/policy self-promotion, unrestricted infrastructure repair and World Intelligence inference remain outside it. Independent mechanical checks do not prove artistic quality or every future game design's compatibility. Preserve the entire preview data directory, ledger, artifacts and canonical history when backing up this local deployment. Earlier failed-attempt outputs are retained; `real-acceptance.json` and `final-verification.json` identify the completed run.
